# Разбор: `memory_retrieve` висит и отваливается по таймауту (memory.db 334 МБ)

> Составлено 2026-08-14. Повод — обращение сессии-тимлида из проекта 1pix.biz: `memory_retrieve`
> в namespace `woo-crm` висит, `curl POST /mcp` с верным токеном отдаёт HTTP 000 за 20 с,
> контейнер `ruflo` жжёт 89 % CPU при 1.27 GiB RAM. Разбор — по исходникам `ruflo`
> (`@claude-flow/cli` → `dist/src/memory/memory-initializer.js`) плюс замеры на синтетической
> копии базы того же размера и формы. Ничего разрушающего на проде не выполнялось.

---

## TL;DR

Дело **не в размере файла как таком** и **не в перестроении HNSW**. Дело в том, что на
sql.js-фолбэке **каждая операция памяти — включая чтение — целиком перезаписывает весь файл
базы, и делает это дважды**, синхронно, под глобальным файловым локом.

- `memory_retrieve` = `getEntry()` → инкремент `access_count` → `db.export()` → атомарная запись
  всех 334 МБ. Плюс перед этим `ensureSchemaColumns()` — **ещё один полный read-modify-write**,
  который на текущей схеме срабатывает **всегда**, даже когда менять нечего (см. «Дефект №1»).
- Замер на 302-МБ копии: **один цикл — 4.9 с** (тёплый кеш) / **7.8 с** (холодный), из них
  3.9–4.6 с — атомарная запись с `fsync`. Значит одна `memory_retrieve` ≈ **10 с**.
- Лок `memory.db.lock` считается «протухшим» через **10 с** и отбирается другим вызовом, а
  таймаут его захвата — **15 с**. Операция длиннее 10 с ⇒ лок отбирают на ходу ⇒ два
  конкурентных whole-image write ⇒ **строки проигравшего молча исчезают**. Это ровно тот failure
  mode, от которого лок и вводили (upstream #2878) — размер базы его снова открыл.
  **Прямо сейчас записи в `woo-crm` могут теряться без ошибки.**
- 99.6 % базы — namespace `pattern`, который **пишет наш собственный хук**
  (`templates/intelligence-bridge.cjs` ← `hook-handler.cjs`) по строке на каждый вызов Bash/Edit
  в каждом проекте. Без TTL, без потолка, ключ уникальный (`pattern-<ts>-<rand>`) — то есть
  никогда не перезаписывается.
- После удаления namespace `pattern` тот же цикл на той же машине — **36 мс** вместо 4.9 с
  (×135), база 1.3 МБ вместо 302 МБ.

## Цепочка причин

Все шесть точек входа sql.js-фолбэка (`storeEntry`, `searchEntries`, `listEntries`, `getEntry`,
`deleteEntry`, `purgeNamespace`) устроены одинаково:

```
withMemoryDbLock(memory.db)                    ← advisory O_EXCL лок на файл
  └─ ensureSchemaColumns(memory.db)            ← ЦИКЛ 1: read 334 МБ → open → export → write 334 МБ
  └─ readFileMaybeEncrypted(memory.db)         ← ЦИКЛ 2: read 334 МБ
     new SQL.Database(buffer)                  ←         копия 334 МБ в Emscripten MEMFS
     SELECT / UPDATE / INSERT                  ←         единицы мс — сама работа дешёвая
     db.export()                               ←         сериализация всех 334 МБ
     writeFileRestricted(…)                    ←         tmp-файл + fsync + rename, 334 МБ
```

`memory_stats` и `memory_list` (их дёргает **наш собственный** `GET /stats`) идут через
`listEntries({limit: 100000})`: цикл 1 (полная запись!) + чтение всех 35 979 строк, причём в
`SELECT` включена колонка `embedding`, хотя используется только флаг `hasEmbedding` — в JS
материализуется **278 МБ текста векторов**.

### Дефект №1 — `ensureSchemaColumns` помечает образ грязным всегда

`memory-initializer.js`, `ensureSchemaColumns()`:

```js
if (columnsAdded.includes('status') || existingColumns.has('status')) {
    try { db.run(`UPDATE memory_entries SET status = 'active' WHERE status IS NULL`);
          modified = true; }        // ← выставляется безусловно, даже при 0 изменённых строк
    catch { }
}
…
if (modified) { const data = db.export(); writeFileRestricted(dbPath, Buffer.from(data), …); }
```

Колонка `status` в нашей базе есть ⇒ ветка берётся всегда ⇒ `modified = true` всегда ⇒
**каждая операция памяти платит лишний полный write всего файла**. Починка в одну строку:
проверять `db.getRowsModified() > 0`, а не факт наличия колонки.

### Версия на проде: cli 3.14.2 — лока НЕТ вообще

Контейнер поднят 7 недель назад, значит в образе `ruflo` ≈ 3.14.2 (`@claude-flow/cli@3.14.2`,
опубликован 2026-06-25 — совпадает с коммитом «adopt upstream leak fix (ruflo 3.14.2)»).
Проверено по тарболлу именно этой версии, а не по `latest`:

| | 3.14.2 (прод) | 3.38.9 (текущий npm) |
| --- | --- | --- |
| `withMemoryDbLock` | **отсутствует** | есть (10 с stale / 15 с acquire) |
| `hasNativeWalSidecars` (гейт #2735) | **отсутствует** | есть |
| `ensureSchemaColumns` → `modified = true` безусловно | есть | есть |

Версия подтверждена данными с прода — `https://ruflo.1pix.biz/health` (endpoint локальный, MCP не
дёргает, лока не берёт, стоит ноль):

```

currentConnectedSince  2026-08-14T11:26:59Z

```

Отдельно стоит `lastChildRespawnRssMB = 7666` при пороге `3000`: watchdog опрашивает RSS раз в
60 с, значит между двумя опросами процесс вырос примерно на 4.6 ГБ — это несколько одновременных
whole-image операций по ~1.3 ГБ транзиента каждая. При `mem_limit 8g` это вплотную к cgroup-OOM,
то есть порог 3000 при текущем размере базы уже не выполняет свою функцию. `childRssMB 1310` в
момент опроса — одна операция в полёте.

Практические следствия, важные для оценки риска:

- Дефект №2 ниже (протухание лока) к проду **не относится** — там нет никакого лока. Это не
  лучше, а хуже: конкурентные whole-image записи **вообще ничем не сериализованы**, и каждая
  пара пересёкшихся операций теряет строки проигравшего целиком. При длительности операции
  ~5–10 с, четырёх живых сессиях и опросе statusline пересечение — норма, а не край.
- Отсутствие гейта #2735 объясняет, почему операции не отказывают при живом `memory.db-wal`
  (см. ниже), а честно висят по 20 с. И одновременно это **предупреждение к апгрейду**: как
  только `ruflo` обновится до версии с гейтом, при наличии `-wal`/`-shm` рядом с `memory.db`
  **каждая** операция памяти начнёт возвращать отказ, пока сайдкары не убраны.

### Дефект №2 — лок протухает быстрее, чем длится операция (в версии 3.38.9; на проде лока нет)

```js
const MEMORY_DB_LOCK_STALE_MS = 10_000;            // после этого лок отбирают как «протухший»
const MEMORY_DB_LOCK_ACQUIRE_TIMEOUT_MS = 15_000;  // после этого — «timed out acquiring memory.db lock»
```

`mtime` лок-файла ставится один раз при создании и не обновляется по ходу работы. Измеренная
длительность одной операции (≈10 с с учётом дефекта №1) вплотную подходит к порогу протухания,
а под очередью — превышает его. Отсюда одновременно оба симптома: и `Request timed out` (44 шт.
за час в логе), и **тихая потеря строк**.

### Дефект №3 — векторы лежат текстом

`embeddingJson = JSON.stringify(embResult.embedding)` — 384 float пишутся десятичными
разложениями float64 в TEXT-колонку: **≈8 КБ на запись против 1.5 КБ** у бинарного
`Float32Array` (замер коллеги — 8 035 байт средних, сходится). Итого 276 из 334 МБ — векторы.
Это ×5 к цене всех циклов выше. Починить снаружи нельзя: все читатели делают
`JSON.parse(embeddingJson)`, формат меняется только апстримом.

## Замеры

Синтетическая копия: 35 830 строк в namespace `pattern` + 149 в `woo-crm`, 384-мерные векторы
JSON-текстом, та же схема — **302 МБ** (у вас 334 МБ). Один цикл `getEntry`, macOS/NVMe:

| фаза | тёплый кеш | холодный |
| --- | --- | --- |

| `SELECT` по ключу | 18 мс | 15 мс |
| `UPDATE access_count` | 95 мс | 6 мс |
| `db.export()` | 97 мс | 172 мс |
| атомарная запись + `fsync` 302 МБ | **3 872 мс** | **4 616 мс** |
| **итого один цикл** | **4 862 мс** | **7 820 мс** |

Читающая половина `memory_stats` на той же базе: 4 839 мс, из них 1 592 мс — материализация

## Ответы на исходные гипотезы

1. **«sql.js держит базу целиком в памяти, и на 334 МБ операции не укладываются в таймаут»** —
   вывод верный, механизм нет. Резидентность не при чём: `new SQL.Database` из готового буфера
   — 3 мс. Не укладывается в таймаут **синхронная перезапись всего файла на каждой операции**
   (и дважды из-за дефекта №1). Размер — множитель, дефект — O(размер файла) на операцию.
   **Перестроение HNSW на каждой операции — опровергнуто**: индекс кешируется на уровне модуля
   (`getHNSWIndex`) и собирается один раз на процесс, максимум 10 000 записей. Но это значит,
   что **каждый респавн от RSS-watchdog'а** оплачивает пересборку заново (10 000 × `JSON.parse`
   8-КБ вектора) — то есть watchdog при таком размере базы делает хуже, а не лучше.
2. **«Векторы текстом вместо блоба — пятикратный перерасход»** — подтверждено, см. дефект №3.
   Цена перехода: правка апстрима, снаружи не лечится.
3. **«`pattern-store` пишет на каждый вызов без TTL и потолка»** — подтверждено, и источник —
   **наш репозиторий**. `templates/hook-handler.cjs:186,192` вызывает `ibCall('step', …)` на
   `post-edit` и `post-bash`, `templates/intelligence-bridge.cjs:91` шлёт
   `hooks_intelligence_pattern-store`. Хендлер апстрима (`hooks-tools.js:3011`) складывает это в
   namespace `pattern` с ключом `pattern-<ts>-<rand>` — уникальным, то есть без upsert — и
   `storeEntry` вызывается **без `ttl`**. Ни потолка, ни вытеснения нет.
   Читатели у namespace `pattern` существуют: `hooks_intelligence_pattern-search`,
   `agentdb_pattern-search`, `memory_search_unified`. Судить по `accessCount` действительно
   нельзя (его двигает только `getEntry` по точному ключу). Надёжный способ — грепнуть лог
   сервера по именам этих инструментов: в вашем окне 500 строк их **ноль**, при 182 записях за
   тот же час. То есть namespace фактически write-only.

## Что делать

### Безопасно, без рестарта и без касания данных

1. **Перестать наращивать базу — правка в нашем репо.** Сделать pattern-store в
   `templates/intelligence-bridge.cjs` выключаемым/сэмплируемым (env-флаг, дефолт — выкл. или
   1 из N), убрать `step()` с `post-bash`/`post-edit` как безусловный. Это снимает ~182
   записи в час, а значит ~364 полных перезаписи файла в час.
2. **Убрать амплификацию из нашего же `/stats`** (`server.mjs:445,457`). `memory_stats` и
   `memory_list` — самые дорогие инструменты, какие есть на этой базе (по полной перезаписи
   файла каждый, плюс 278 МБ материализации). Клиентский таймаут 2 с **не отменяет** работу в
   child-процессе — вызов всё равно доходит до конца. `statusline.cjs` кеширует `/stats` на
   120 с, то есть 4 сессии дают ~240 таких вызовов в час на ровном месте. `dbSizeKB` считается
   из файлов и не требует MCP вообще — счётчик записей стоит либо убрать, либо спрятать за
   env-флаг.
3. Со стороны 1pix.biz: перевод сторожа с 1 мин на 5 мин уже уменьшил долю; после пункта D
   цена одного чтения падает до десятков мс и вопрос снимается.

### Требует решения человека (разрушающее)

4. **Вычистить namespace `pattern`.** Это возвращает базу к 1–2 МБ и цену операции к ~36 мс.
   Важно: **делать офлайн**, а не через MCP — удаление через `memory_cleanup`/`deleteEntry`
   означает 35 830 полных перезаписей файла. Порядок: снять бэкап volume → остановить
   контейнер → `DELETE FROM memory_entries WHERE namespace='pattern'` + `VACUUM` →
   удалить `hnsw.index` и `hnsw.metadata.json` (иначе индекс загрузится с диска и не
   пересинхронизируется с БД: `getHNSWIndex` при непустом индексе пропускает синк, и в выдаче
   останутся id удалённых строк) → поднять контейнер. `woo-crm` не трогать.
   Рестарт оборвёт in-flight вызовы четырёх сессий — согласовать окно.
5. **Решить, на чём жить дальше.** Корень в том, что работает sql.js-фолбэк, а не нативный
   AgentDB-мост. Что мост лежит — видно без всякой диагностики: `hooks_intelligence_pattern-store`
   сначала пробует `bridgeStorePattern` и только при его отказе падает в `storeEntry`
   (`hooks-tools.js:3041`). Раз 35 830 строк лежат в `memory.db` в namespace `pattern` — значит
   мост отказывал все эти месяцы. **Это утверждение опровергнуто — см. раздел «ПОПРАВКА» ниже:**
   в 3.14.2 мост работает и делит `memory.db` с whole-image путём, а `pattern`-строки в `memory.db`
   про состояние моста не говорят ничего, потому что оба пути пишут один файл.
   Что действительно нужно решить — почему инициализация реестра проходит не в каждом поколении
   процесса (латчится на всю его жизнь), и это остаётся за диагностикой решения 0.
   Подводный камень апгрейда, наоборот, стал жёстче: **с 3.15 мост уезжает в отдельный файл**
   `agentdb-memory.db` (`memory-bridge.js:getAgentDbPath`, #2786), а `bridgeGetEntry` на промахе
   возвращает `{success:true, found:false}` — значение **истинное**, фолбэка на `memory.db` не
   будет. Сегодня все данные лежат в `memory.db` и читаются через мост; после апгрейда без миграции
   они станут невидимыми — не «возможно», а гарантированно.
   Порядок: `memory_export` → апгрейд → `memory_import` → проверить.

## ПОПРАВКА: мост жив, и в 3.14.2 он работает по тому же `memory.db`

Раннее утверждение этого документа — «AgentDB-мост мёртв, 35 830 строк в `memory.db` доказывают,
что он отказывал месяцами» — **неверно**. Доказательство от соседней сессии: `memory_store` вернул
`storeTime` **1.26 мс** и **9.88 мс** при том же 336-МБ файле. `storeTime` в 3.14.2 оборачивает
**весь** вызов `storeEntry()` (`mcp-tools/memory-tools.js`: `startTime` до вызова, `duration` сразу
после), то есть whole-image путём это быть не может физически — там одна атомарная запись 336 МБ
занимает секунды.

Причина найдена в 3.14.2:

```js
await registry.initialize({
    dbPath: dbPath || getDbPath(),      // ← getDbPath() = <memoryRoot>/memory.db
```

`getAgentDbPath` в 3.14.2 **не существует вовсе** (0 вхождений) — разделение на отдельный
`agentdb-memory.db` появилось позже, вместе с #2786. Значит в этой версии AgentDB открывает
**сам `memory.db`** через нативный `better-sqlite3` и ставит `journal_mode = WAL`. Отсюда сразу
три следствия, отменяющие прежние выводы:

1. **`better-sqlite3` в образе ЕСТЬ.** Два независимых признака: живой растущий `memory.db-wal`
   (sql.js его создать не может) и субмиллисекундные записи. Ранний вывод «MISSING» был артефактом
   моей неверной команды проверки (разрешение из `/app` вместо каталога глобального пакета).
2. **Отсутствие `agentdb-memory.db` — норма для этой версии**, а не признак падения инициализации.
   Прежнее рассуждение «нативный `new Database(path)` создал бы файл сразу, значит мост падает
   раньше» опиралось на путь из 3.38.9 и к проду не применимо.
3. **Основной нативный писатель `memory.db` — сам мост**, а не только `graph-edge-writer`.

### Что тогда объясняет всплески

`bridgeAvailable = false` **латчится на всё время жизни процесса**. Значит поведение задаётся
поколением процесса: если инициализация реестра в конкретном `ruflo mcp start` прошла — все
операции идут нативным путём и стоят миллисекунды; если не прошла — весь остаток жизни этого
процесса работает sql.js-фолбэк по 336-МБ файлу, по 10–21 с на операцию. При девяти респавнах
(`childRespawnCount 9`) поколений много, и «то лежит, то летает» — это ровно смена поколения, а не
меняющаяся нагрузка. Формулировка соседней сессии «отвечает, но нестабилен» точнее, чем «лежит».

Из этого же следует, что чистка базы остаётся полезной, но её роль другая: она не «лечит
медленную память», а **делает аварийный путь дешёвым** — 36 мс вместо 10 с в тех поколениях, где
мост не поднялся. Корневой вопрос — почему инициализация реестра иногда не проходит; ответ на него
даёт только диагностика из решения 0.

### И это делает dual-write race серьёзнее, чем описано ниже

Ниже говорится про `graph-edge-writer` как нативного писателя. В 3.14.2 главный нативный писатель —
**мост**, обслуживающий обычные `memory_store`. То есть в одном файле сходятся: нативные WAL-записи
живого поколения и полные перезаписи образа (`db.export()` + `rename`) деградировавшего поколения,
**без какого-либо лока** (`withMemoryDbLock` в 3.14.2 отсутствует). Полная перезапись, построенная
из образа без WAL-содержимого, затирает закоммиченные нативно строки молча. Это ровно тот симптом,
который апстрим описал в #2431 как `database disk image is malformed (11)`.

Практический вывод для координации: успешный ответ `memory_store` **не** означает, что строка
переживёт следующую whole-image запись. Правило «перечитывать ключ после записи» остаётся
обязательным — и перечитывание тоже не гарантия, если между ними вклинилась перезапись образа.

### Найденный механизм деградации — в нашем коде, не в апстриме

`StdioClientTransport.close()` (прочитан прямо из контейнера) закрывает stdin, ждёт до 2 с, шлёт
SIGTERM, ждёт ещё 2 с и только тогда SIGKILL — и возвращается, не подтверждая фактический выход.
А `connectToRuflo()` вызывал `close()` **fire-and-forget** и спавнил нового ребёнка сразу. То есть
старый `ruflo mcp start` жил ещё несколько секунд после старта нового, **держа нативное
WAL-соединение к `memory.db`**. Два поколения на одном файле дают:

1. DDL/schema-шаг нового ребёнка может получить `SQLITE_BUSY` от старого. `initAgentDB()` это
   глотает (`catch` → `emit('agentdb:unavailable')` в никуда → `agentdb = null`) и **не бросает**,
   поэтому `bridgeAvailable` латчится в `false` на всю жизнь процесса — и всё поколение уходит на
   sql.js whole-image путь. Это лучшее объяснение «то летает, то висит»: режим задаётся поколением.
   AgentDB при открытии ставит только `journal_mode = WAL` и **не** ставит `busy_timeout`
   (в отличие от `graph-edge-writer`, где стоит 5000 мс) — то есть занятость не переживается, а
   превращается в мгновенную ошибку.
2. Если старый ребёнок в этот момент делает whole-image запись, она затирает нативно закоммиченные
   строки — апстримный #2431.

Исправлено в `server.mjs`: респавн теперь **дожидается** выхода старого ребёнка (`waitForChildExit`),
проверяет исчезновение pid по `/proc`, добивает `SIGKILL` при необходимости и только потом спавнит
нового. Таймаут — `RUFLO_OLD_CHILD_EXIT_TIMEOUT_MS`, по умолчанию 8000 мс.

Гипотеза про `SQLITE_BUSY` остаётся гипотезой: `initAgentDB` ошибку не логирует, поэтому прямого
доказательства из лога получить нельзя. Но перекрытие поколений — факт (код `close()` + fire-and-forget
вызов), и устранять его нужно независимо от того, какая именно ошибка внутри латчит мост.

### Режим стало видно снаружи

В `/health` добавлено поле `childMemoryRegime`: `native` — ребёнок держит fd на `memory.db-wal`
(мост жив, операции миллисекунды), `fallback` — не держит (каждая операция перезаписывает весь
образ, 10–21 с), `null` — `/proc` недоступен. Раньше два режима снаружи не различались, поэтому
«ruflo медленный» и не удавалось прижать.

**Известное ограничение индикатора.** Сразу после старта контейнера поле показывает `fallback`,
даже когда мост в порядке: файл `-wal` появляется только при первом обращении к базе, а индикатор
смотрит именно на его fd. Проверено 2026-08-15: после пересоздания контейнера поле читалось как
`fallback`, один `memory_list` — и оно переключилось на `native`. Поэтому `fallback` сразу после
рестарта означает «ещё не знаю», а не «плохо». Планируемая правка — считать вызовы `memory_*` с
момента старта child'а и отдавать `unknown`, пока счётчик нулевой.

## Второй писатель в том же файле: живой `memory.db-wal`

На проде рядом с базой лежат `memory.db-wal` (4.2 МБ) и `memory.db-shm`, причём **свежее самой
базы** (12:50 против 12:48). sql.js WAL не умеет и создать эти файлы не может. Источник найден —
`cli/dist/src/memory/graph-edge-writer.js` (есть и в 3.14.2):

```js
const dbPath = customDbPath ?? path.join(getMemoryRoot(), 'memory.db');   // ← ИМЕННО memory.db
…
const db = new BetterSqlite3(dbPath);
db.pragma('journal_mode = WAL');
```

Вызывается из `mcp-tools/hooks-tools.js` и `mcp-tools/agentdb-tools.js` — то есть с тех же
hook-инструментов, которые дёргают наши хуки. Апстрим в шапке модуля описывает ситуацию сам
(«#2431 fix (2026-06-22)»): прежняя sql.js-версия писала `fs.writeFileSync(dbPath, db.export())`
после каждой вставки ребра и «перезаписывала основной `memory.db`, пока better-sqlite3-мост писал
через свой WAL — тот самый dual-write race», симптом — `database disk image is malformed (11)`.

**Их фикс не закрывает проблему, а только переносит её.** Формулировка «WAL делает конкурентных
писателей безопасными по built-in дизайну SQLite» верна для двух SQLite-**соединений** и неверна
здесь: остальные пять точек входа в той же версии продолжают делать `db.export()` + атомарный
`rename` поверх того же пути. Переименование подменяет файл под живым нативным соединением: его
fd остаётся на отвязанном inode, WAL перестаёт соответствовать новому образу, и
**закоммиченные нативно строки исчезают без ошибки** (SQLite при несовпадении salt просто
сбрасывает журнал). То есть на проде сейчас три несогласованных писателя одного файла: два
whole-image пути и одно нативное WAL-соединение.

Проверяемое следствие: снимок через `docker cp` копирует только `memory.db` **без** `-wal`,
поэтому он WAL-слепой. В снимке `graph_edges` почти наверняка выглядит пустой, хотя строки есть —
они в тех 4.2 МБ журнала. Censo «38 таблиц, непустых три» этим и объясняется.

### Что это меняет в плане чистки

Порядок из пункта 4 дополняется обязательным шагом: **сначала свести журнал в образ нативным
соединением** (`PRAGMA wal_checkpoint(TRUNCATE)`), и только потом `DELETE` + `VACUUM`. Делать это
**нельзя через sql.js** — он WAL игнорирует, и checkpoint'а не произойдёт, а первая же
whole-image запись выбросит журнал целиком. Порядок: снять бэкап volume вместе с `-wal`/`-shm` →
остановить контейнер (чтобы не осталось писателей) → нативный `wal_checkpoint(TRUNCATE)` →
`DELETE FROM memory_entries WHERE namespace='pattern'` → `VACUUM` → поднять контейнер.
`hnsw.index` и `hnsw.metadata.json` на этой установке отсутствуют, так что удалять их не нужно —
индекс живёт только в памяти процесса и соберётся при первом обращении (один дорогой вызов).

## Почему отказ моста не виден в логе (и чем его диагностировать)

Проверка коллеги по `/app/.swarm/ruflo-stderr.log` (`grep -c "better-sqlite3 not available"` → 0,
ни одного упоминания `bridge|sqlite|native`, при штатных `ONNX embedder ready: 384d, SIMD: true`)
**не является доказательством, что `better-sqlite3` загрузился**. Эта строка не может попасть в
stderr-лог по построению:

- пишет её `console.log` — то есть **stdout**, а в stdio-режиме MCP это канал протокола, а не тот
  файл, куда `server.mjs` складывает stderr ребёнка;
- и она **дважды отфильтрована явно**: `ControllerRegistry.initAgentDB` подменяет `console.log`
  на время инициализации фильтром `msg.includes('Transformers.js') || msg.includes('better-sqlite3')
  || msg.includes('[AgentDB]')`, а `memory-bridge.js` держит тот же список в `INIT_LOG_NOISE`.
  Сообщение `agentdb`'а — ровно `[AgentDB] better-sqlite3 not available, using sql.js WASM` —
  попадает под оба фильтра. Итоговая строка режима (`[AgentDB] Initialized with sql.js WASM …`)
  подавлена так же.

Тишина в логе, таким образом, ожидаема при **любом** исходе, и режим по логу не определить.

Хуже того, отказ латчится **без ошибки**: `ControllerRegistry.initAgentDB` ловит всё,
эмитит `agentdb:unavailable` (слушателей нет), ставит `this.agentdb = null` — и **не бросает**.
Поэтому `registry.initialize()` завершается успешно, `bridgeAvailable = true`,
`bridgeFailureReason = null`, а `getDb(registry)` возвращает `null`, потому что
`registry.getAgentDB()?.database` пустой ⇒ каждая функция `bridge*()` возвращает `null` ⇒ все
вызовы молча уходят на sql.js whole-image путь. **«Мост доступен» ≠ «мост используется».**

**`memory_bridge_status` для диагностики не годится — не вызывать.** Во-первых, он опрашивает
`listEntries` **девять раз** (все записи + `claude-memories` + семь namespace'ов), а каждый
`listEntries` — это полный read-modify-write всего файла: на 334-МБ базе получается ~90 с и ~3 ГБ
записи. Во-вторых, он всё равно не ответит: `isBridgeAvailable()` отдаёт `bridgeAvailable`,
который равен `true` при любом не-брошенном `initialize()`.

Правильные проверки — обе без единого MCP-вызова, без лока и мгновенные:

```bash
# 1. Состав каталога и наличие сайдкаров (это работает как есть)
docker exec ruflo ls -la /app/.swarm/

# 2. Есть ли нативный биндинг — ВАЖНО: разрешать из каталога пакета ruflo, а не из /app
docker exec ruflo find /usr/local/lib/node_modules -maxdepth 5 -type d -name better-sqlite3
docker exec -w /usr/local/lib/node_modules/ruflo ruflo \
  node -e "try{console.log(require.resolve('better-sqlite3'))}catch(e){console.log('MISSING: '+e.message)}"

# 3. Кто прямо сейчас держит файл открытым (виновник WAL)
docker exec ruflo sh -c 'for f in /proc/[0-9]*/fd/*; do l=$(readlink "$f" 2>/dev/null); \
  case "$l" in */memory.db*) echo "$f -> $l";; esac; done'

# 4. Почему мёртв AgentDB-мост — импорт из контекста пакета
docker exec -w /usr/local/lib/node_modules/ruflo ruflo \
  node -e "import('agentdb').then(m=>console.log('ok',Object.keys(m).slice(0,5)),e=>console.log('FAIL',e.message))"
```

**Про пункт 2 — важная поправка.** `docker exec ruflo node -e "require('better-sqlite3')"`
(вариант, который стоял здесь раньше) **даёт ложный «MISSING»**: `ruflo` установлен глобально в
`/usr/local/lib/node_modules/ruflo`, а `node -e` с рабочим каталогом `/app` ищет только в
`/app/node_modules` и `/node_modules` — глобальное дерево в путь разрешения не входит. Проверять
надо из каталога пакета (`-w`) или через `require.resolve(..., { paths: [...] })`.

Живой, растущий `memory.db-wal` со свежим mtime — свидетельство, что нативный биндинг **на месте**.
Раздел «ПОПРАВКА» выше это подтверждает с другой стороны (субмиллисекундные записи), и там же снято
прежнее рассуждение про `agentdb-memory.db`: в 3.14.2 этого файла и не должно быть, мост работает по
`memory.db`. Поэтому проверки 2–4 нужны уже не для ответа «жив ли мост» (жив), а для другого
вопроса — **почему он поднимается не в каждом поколении процесса**: пункт 4 покажет, разрешается ли
модуль `agentdb` вообще, а пункт 3 — сколько сейчас держателей файла и кто они.

### Апстрим (`ruvnet/ruflo`) — тикеты, все мелкие и точные

6. `ensureSchemaColumns` выставляет `modified = true` при наличии колонки `status`, а не по
   факту изменённых строк ⇒ лишний полный write образа на **каждой** операции чтения и записи.
7. `MEMORY_DB_LOCK_STALE_MS` (10 с) меньше длительности одной whole-image операции на большой
   базе, `mtime` лока не обновляется ⇒ протухание на ходу ⇒ конкурентные перезаписи и молчаливая
   потеря строк — тот самый #2878. Нужно либо heartbeat лока, либо порог от размера файла.
8. `embedding` хранится JSON-текстом (×5 к объёму); `listEntries`/`memory_stats` тянут колонку
   `embedding` в `SELECT`, хотя используют только `hasEmbedding`.
9. Отказ AgentDB латчится молча и недиагностируемо: `initAgentDB` ловит ошибку, эмитит
   `agentdb:unavailable` в никуда и не бросает, поэтому `bridgeAvailable = true` и
   `bridgeFailureReason = null` при полностью нерабочем мосте; единственная строка, называющая
   режим, подавлена собственным лог-фильтром. `isBridgeAvailable()` должен учитывать
   `getAgentDB()?.database`, а не только факт непадения `initialize()`.
10. `memory_bridge_status` — диагностический инструмент, который на большой базе стоит девять
    полных перезаписей файла (девять вызовов `listEntries`). Диагностика не должна быть самой
    дорогой операцией в системе.
11. **Главный, вероятно:** фикс #2431 не устранил dual-write race, а сузил его. `graph-edge-writer`
    держит нативное WAL-соединение к `memory.db`, тогда как `storeEntry`/`getEntry`/`listEntries`/
    `searchEntries`/`deleteEntry` в той же версии продолжают делать `db.export()` + `rename`
    поверх того же пути. WAL защищает конкурентные SQLite-соединения, но не защищает от подмены
    файла целиком: после `rename` нативный fd смотрит на отвязанный inode, журнал перестаёт
    соответствовать образу, и закоммиченные строки исчезают молча. Либо все писатели нативные,
    либо все whole-image — смешивать нельзя.

## Апгрейд невозможен без починки моста (проверено)

`graph-edge-writer` открывает `memory.db` нативно и в WAL-режиме **и в 3.14.2, и в 3.38.9**
(в обеих версиях `dbPath = path.join(getMemoryRoot(), 'memory.db')`). А начиная с 3.15 sql.js-пути
отказывают, пока рядом лежат `-wal`/`-shm`. Значит на любой свежей версии последовательность
такая: первый же hook-вызов, пишущий ребро графа, создаёт `memory.db-wal` → и после этого
**каждая** `memory_store`/`memory_retrieve`/`memory_search` возвращает `walRefusalError`, пока
работает sql.js-фолбэк. Чекпоинт и удаление сайдкаров помогают ровно до следующего ребра.

Отсюда вывод, меняющий порядок решений: «починить нативный мост» — это **не альтернатива**
апгрейду, а его **предусловие**. Свежие версии рассчитаны на то, что операции идут через
AgentDB-мост, а sql.js-путь там — аварийный и при живом WAL заведомо закрытый.

## Как обновление доезжает до прода (и почему `docker compose pull` сейчас опасен)

На проде **нет исходников** — только `docker-compose.yml`, и он тянет готовый образ:

```
/home/woo-crm/ruflo-hub/docker-compose.yml → image: jazzmax/ruflo-hub:latest
запущенный образ создан 2026-06-26T12:16Z, контейнер поднят 12:20Z
volumes: ruflo-hub_ruflo-memory / ruflo-hub_ruflo-state — external, recreate их НЕ трогает
```

Отсюда важное: CI пересобирает `:latest` еженедельно, но прод **не подтягивает автоматически** —
образ на нём от 26 июня. То есть `:latest` в Hub сейчас собран из **незапиненного** `ruflo@latest`,
и это уже 3.38.x. **Любой `docker compose pull` на проде прямо сейчас = тот самый неконтролируемый
апгрейд**, который включит гейт #2735 и остановит память. Пин обязан попасть в образ раньше, чем
кто-нибудь сделает pull.

Правильный порядок:

1. закоммитить и запушить правки (пин 3.14.2 + флаг хука + гейт `/stats` + ожидание выхода
   старого child'а + `childMemoryRegime`);
2. дождаться, пока CI соберёт и опубликует `:latest`; **проверить, что в образе действительно
   3.14.2** — `docker run --rm jazzmax/ruflo-hub:latest npm ls -g --depth=0 | grep ruflo`
   (запечка ONNX-модели в сборке иногда флапает на HuggingFace — тогда повторить сборку);
3. окно: `docker compose pull` → `docker stop` → `scripts/prune-memory-namespace.sh --yes`
   → `docker compose up -d` (одно окно на всё, а не два);
4. в каждом проекте с хуками — `curl <hub>/update-bundle | bash`, иначе `.claude/helpers/` останется
   со старым хуком и поток `pattern`-записей не прекратится: флаг живёт в клиентском файле,
   пересборка образа сама по себе его не выключает.

мост уехал в отдельный `agentdb-memory.db` (#2786), он был создан заново и начал наполняться, а
149 строк `woo-crm` остались в `memory.db`, к которому мост больше не обращается. Отказ **тихий**:
`bridgeGetEntry` на промахе возвращает истинное `{success:true, found:false}`, то есть
`memory_retrieve` отвечает «нет такого ключа», а не ошибкой.

Два правила, которые из этого следуют:

1. **Пинить надо тот пакет, который делает работу.** В Dockerfile теперь пинится и
   `@claude-flow/cli` (`npm install --prefix …/ruflo @claude-flow/cli@<version>`), а сборка
   **падает**, если после установки версия не та. Приём проверен в чистом контейнере:
   до пина `3.38.9`, после — `3.14.2`.
2. **`found: false` от key-value хранилища больше не доказательство отсутствия данных.** У тихого
   отказа и у пустого ключа одинаковый ответ, поэтому «записи нет» подтверждать вторым способом —
   прямым чтением файла (`sqlite3`), а не только через MCP.

Приёмочная проверка образа перед развёртыванием — не только версия, но и поведение: в одноразовом
контейнере сделать `ruflo memory init` + `memory store` и убедиться, что строка легла в
`memory.db`, а не в `agentdb-memory.db`.

## Как это соотносится с уже известной утечкой

`UPSTREAM-ISSUE-sqljs-memfs-leak.md` и `LEAK-INVESTIGATION-HANDOFF.md` описывают, как
осиротевшие `dbfile_*` в MEMFS растят RSS. Это **другая** проблема, но с общим корнем — «на
каждую операцию открывается полный образ базы». Наш build-time патч
(`scripts/patch-sqljs-leak.cjs`) кеширует бэкенды `@claude-flow/memory`, но путь
`memory-initializer.js` от него не зависит: он делает `import('sql.js')` и
`new SQL.Database(...)` напрямую, поэтому текущие симптомы патч не покрывает.
В июне база была ~150–178 МБ (см. handoff), сейчас 334 МБ — то есть деградация плавная и
предсказуемая: цена каждой операции линейна по размеру файла, а файл растёт от нашего же хука.
